# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**`README.md` is the complete spec** — the what, why, hardware, message set, intended layout, and references. Read it before any implementation work. This file does not restate the spec; it only covers how to *operate* in the repo.

## Status & operating constraints

- **All six phases work end to end on hardware.** `gateway/` is a working Zephyr **C++** app (see `notes/language-cpp.md`), now **four threads** across **five translation units**, one responsibility each: `sensor.cpp` (acquisition — reads the SCD-40 over I²C via the sensor API and publishes to a **zbus** channel), `protocol.cpp` (the wire format — the only place internal types meet nanopb/protobuf), `commands.cpp` (command semantics — dispatch, duplicate suppression, node identity), `relay.cpp` (the CAN side — two threads), and `main.cpp` (the MQTT sessions — IPv4 on the on-board Ethernet, publish `Telemetry`, answer `Command`s with `Ack`s). **Only three of those five live in `gateway/src/`** — `protocol.cpp` and `commands.cpp` are in `shared/`, compiled by relative path, because the peer node links the very same files; see the layout bullet below. The split is what makes the middle two testable without hardware. They meet on the channels in `shared/app_channels.h` — read its header comment before touching either side. `proto/` holds the schema; `host/` holds the Python paho harness (`monitor.py`, `command.py`) — run it **on the Pi**, which is the only machine that can reach the broker. Verified against the bench: telemetry decode, all three commands, out-of-range rejection, duplicate suppression, a malformed payload that did not desync the stream, and a 66 s broker outage the sensor thread sampled straight through. The **schema-versioning exercise** is now done off-target: the `Telemetry` measurements are proto3 `optional` and `pressure_pa` was added for the peer node, and `tests/protocol/` hand-builds a descriptor for the previous schema with nanopb's `PB_BIND` X-macro so old↔new runs in both directions on qemu. The *dumb-gateway* payoff is now shown on hardware too: node 1 publishes `co2_ppm` with no `pressure_pa` and node 2 the reverse, each absent measurement rendering as `--` rather than a fabricated zero, through a gateway that decodes neither payload. What remains undemonstrated is the narrower version — changing the peer's schema and reflashing *only* the peer.
- **The sixth phase is the second node over CAN.** A Nucleo-F072RB with a BME280 is a *peer node* with its own MQTT identity, and the H753ZI is a **gateway** that relays the peer's already-encoded Protobuf without decoding it. Telemetry and commands both cross the bus; `docs/can-bringup.md` steps 6 and 7 are the procedures. What each piece rests on:
  - **Built and verified on a real bus:** two SN65HVD230 transceivers are attached and the two boards share a terminated 500 kbit/s bus. Heartbeats cross it and are acknowledged — `peer node 2 is online` on the gateway, and no `gateway unreachable` on the peer — which proves the entire physical layer at once, since a lone node cannot complete a transmission. Wiring table and procedure: `docs/can-bringup.md` *Bring-up checks* step 6. Internal loopback (steps 1–5) stays the bisect for "firmware or wiring?".
  - **Built and verified off-target:** the CAN *transport*, in `tests/isotp_loopback/`, which runs the emulated `zephyr,can-loopback` controller under qemu via a board overlay. Segmentation and reassembly at the gateway's worst case (161 bytes — FF, FC, 23 CFs), the message-type byte's position after reassembly, `can_link.h`'s identifiers actually being matched by a receive filter, and a packed heartbeat surviving a real frame. **Know its limit:** `can_loopback.c` invokes *every* filter a frame matches where real controllers invoke only the first, so an address map giving two ISO-TP contexts one identifier passes here and fails on both boards. Properties about the constants alone belong in `tests/heartbeat/`, which needs no controller — see `docs/test-strategy.md`.
  - **Verified on a peer:** the whole `peer-node/` app for the F072RB — BME280 acquisition, heartbeat cadence, the ISO-TP round trip in both directions, command handling. 51 % flash / 66 % RAM. Its telemetry reaches `node/2/telemetry` and a `GetDeviceInfo` comes back carrying `board: nucleo_f072rb`, which only the F072RB image contains. The address map gives flow control identifiers of its own (`0x7E4 + n`, `0x7EC + n`, four peers max, `kMaxPeerNodeId`) — see the constraint bullet below. Error codes in `docs/can-bringup.md`.
  - **Verified against a peer, including an outage:** the gateway's `relay.cpp` + `relay.h` — two threads (RX reads the link and owns the liveness clock, TX writes it), four zbus channels, and `main.cpp` publishing the peer's payloads to `node/2/{telemetry,ack,status}` and routing `node/2/command` down. The serve loop is six descriptors and one deadline. Both directions run on the bench (`docs/can-bringup.md` step 7), and step 8 covers unplugging the bus: liveness times the peer out in 3.5 s, `node/1` is undisturbed, and the link recovers with no reset.
  - **Fully verified, Last Will included:** the second MQTT identity. `main.cpp` is `struct node_session` × 2 (`nucleo-1`, `nucleo-2`) stepped as a state machine from one loop — one thread, one wait, one deadline, six descriptors. The second connection buys exactly one thing and it now demonstrably does it: with the gateway's packets dropped at the Pi, the broker fired **both** wills, each 1.5 × keepalive after its own session's last packet, so `node/2/status` went offline with no firmware in the path. The stagger between them is the evidence that these are two independent clients rather than one connection wearing two names. Transcript and procedure in `docs/mqtt-design.md`.
  - `shared/can_link.h` is the link contract — address map, hand-packed heartbeat frame, the message-type byte above ISO-TP — included by both apps, with `tests/heartbeat/` covering it. `commands.h`'s `kNodeClientId` is an `extern` each app defines. Concepts in `notes/can-guide.md`, decisions and bring-up checks in `docs/can-bringup.md` — steps 6 and 7 now cover the two-node bus and the full round trip. The rule still stands for what remains: write a bench procedure only for what has actually been run.
- **`can_send()` with a NULL callback blocks with no bound, and the timeout argument does not change that.** It waits `K_FOREVER` on completion (`drivers/can/can_common.c:69`); the `k_timeout_t` bounds only the wait for a free TX mailbox. Because the bxCAN driver clears `NART` and sets `ABOM`, an unacknowledged frame is retried forever and never permanently fails — so a lone transmitter blocks for as long as the link is down, taking everything else on that thread with it. `peer-node/src/main.cpp` passes a real completion callback and judges the link on the last *completed* beat. **Pass a callback to `can_send()` in anything that must stay responsive.** Detail in `docs/can-bringup.md` *Driver behaviour worth knowing* and step 8.
- **Two constraints are subtle, silent when violated, and have their own sections in `docs/can-bringup.md`.** *Flow control needs its own identifiers*: Zephyr ISO-TP installs one CAN filter per context and real controllers fire only the lowest match, so two contexts must never share an identifier. *The zbus pool is sized by every channel*: with `CONFIG_ZBUS_MSG_SUBSCRIBER=y`, **every** `zbus_chan_pub()` copies its whole message into a pool buffer before any observer is consulted — listener channels included — so `CONFIG_ZBUS_MSG_SUBSCRIBER_NET_BUF_STATIC_DATA_SIZE` must cover the largest message on *any* channel, and undersizing it corrupts memory with no diagnostic. `static_assert`s in `shared/app_channels.h` and `gateway/src/relay.h` pin the sizes; **adding a channel or growing a message means checking them.** Neither app sets `CONFIG_ASSERT=y`, which is why zbus's own check is compiled out — worth enabling for a bench build.
- **Three directories hold firmware, and the split is deliberate.** `shared/` is the code both apps link — `protocol.{h,cpp}`, `commands.{h,cpp}`, `app_channels.h`, `can_link.h` — and it has **three consumers**: `gateway/`, `peer-node/` and `tests/`, each compiling those files by relative path via a `SHARED` variable in its `CMakeLists.txt`. Nothing in `shared/` may depend on an app; nothing in an app may be depended on by another app. That is why `relay.{h,cpp}` stays in `gateway/src/` (only the gateway relays) and why each app keeps its own `main.cpp` and `sensor.cpp` (the session and the sensor are what differ). **Deliberately not a `zephyr_library`:** the generated `node.pb.h` that `protocol.h` and `commands.h` include is attached to each app's own `zephyr_nanopb_sources(app …)` target, so a separate library would have to re-create that plumbing for no gain. When you add a file, the question is how many apps link it — two means `shared/`.
- **Build / flash / console via the wrapper scripts**, not raw `west` — they source the workspace venv and pass `-s`/`-d` correctly. **All of them take `-a <app>` (or `APP=`) and default to `gateway`**; the board follows from the app, so `-b` is never needed:
  ```sh
  ./scripts/build.sh                   # incremental; -p forces pristine (required after devicetree/Kconfig edits)
  ./scripts/build.sh -a peer-node -p   # the F072RB peer node
  ./scripts/flash.sh -a peer-node      # forces the openocd runner; the board's default runner isn't installed
  ./scripts/console.sh -a peer-node    # serial console @115200 (quit with Ctrl-A then K, not Ctrl-A D)
  ./scripts/build.sh -a peer-node --debug -p   # + a trimmed shell on the peer (bench only)
  ./scripts/probe.sh                   # which ST-LINK and which /dev/cu.* belongs to which app
  ./scripts/cleanup.sh                 # remove build dirs; -a for one app
  ```
  **The peer node's console is output-only by default** — no shell, because a stock one takes 95 % of its 16 KB. `--debug` merges `peer-node/debug.conf` for a trimmed shell with the `can` commands (83 % RAM); it changes Kconfig, so pair it with `-p`. `CONFIG_SENSOR_SHELL` will not fit at all.
  **With both Nucleos attached, always say which one.** `console.sh` refuses to guess and prints `probe.sh`'s table; `flash.sh` resolves the app's probe through `scripts/probes.conf` and passes `--serial`, and **stops rather than flashing a board at random** if it cannot — losing that coin flip writes the wrong image to the wrong part and reports success. `STLINK_SERIAL=` overrides. The mapping is keyed on the ST-LINK serial, not the `usbmodemNNNNNN` name, which moves with the USB port. With one board attached none of this engages.
  The apps are **freestanding**: they build against a shared global west workspace at `~/zephyr-workspace` (**Zephyr v4.4.1**). Details in `docs/toolchain.md`.
- **Host-side tests exist; there is no lint tooling.** `./scripts/test.sh` runs 51 Ztest cases on `qemu_cortex_m3` in ~31 s with no board attached — `tests/protocol/` (the wire format), `tests/commands/` (dispatch, validator rejection, duplicate suppression), `tests/heartbeat/` (the hand-packed CAN frame and address map), `tests/relay/` (the gateway's liveness state machine) and `tests/isotp_loopback/` (the CAN transport through an emulated controller: segmentation and reassembly at the gateway's worst-case size, the type byte's position after reassembly, and a heartbeat reaching a real receive filter). Run them before and after touching `protocol.cpp`, `commands.cpp`, `can_link.h` or `relay.h`. Decisions and what is deliberately *not* covered are in `docs/test-strategy.md`; the concepts are in `notes/testing-guide.md`. Everything below the socket still needs the bench: verification there is build → flash → observe (console, `net` shell commands, or the Pi), and the **lab at the end of each guide** — `communication-guide.md` §9, `can-guide.md` §10, `zbus-guide.md` §10, `protobuf-guide.md` §12, `sensor-api-guide.md` §11, `zephyr-build-system-guide.md` §12, `language-cpp.md` §12, plus *Testing the Last Will* in `mqtt-design.md` and *Bring-up checks* in both `sensor-bringup.md` and `can-bringup.md`. **Write bench results as a procedure someone can re-run — commands, expected output, and what it proves — never as a dated report of a past run.** When behaviour changes, update the lab that covers it.
- **Networking is up:** static IPv4 `192.168.10.2/24`, no gateway, on a direct cable to the Pi at `192.168.10.1`. It is configured *entirely* in `gateway/prj.conf` via `CONFIG_NET_CONFIG_SETTINGS` — `net_config` applies it at boot, so no app code touches interface bring-up. Ping is verified both ways.
- **Decisions already made** (don't reopen without reason). In `docs/toolchain.md`: nanopb integration = the **in-tree module**; sensor driver = the **upstream in-tree `sensirion,scd40`**. In `docs/mqtt-design.md`: **QoS per topic + the topic hierarchy** (`node/<id>/{telemetry,command,ack,status}`; telemetry QoS 0, command/ack QoS 1, retained-will status). In `docs/sensor-bringup.md`: the sensor is **`zephyr,deferred-init`** and `sensor.cpp` initialises it, because a failed init is permanent and only its *timing* is controllable; and the **timed poll stays**, with the SCD-40's republish-on-fast-poll behaviour accepted and documented rather than worked around — read *Accepted limitation* there before touching `SAMPLE_PERIOD_MIN_MS` or believing a sub-5 s cadence. Record new decisions and their rationale in `docs/`.

## Working principles

- The deliverable is fluency in the patterns the README calls out — MQTT client lifecycle (connect/keepalive/reconnect, QoS, topics), zbus as the internal bus, schema versioning, and nanopb on a constrained target — not a polished product. Treat those as the real work.
- When a choice trades simplicity for fidelity to the real firmware↔SW-team contract, prefer fidelity. That is the point of the exercise.
- `proto/` is the single source of truth for the wire format; firmware and host both derive from it. Change the schema there and regenerate — never hand-edit generated code.
- **Documentation is split by kind, not by topic: guides live in `notes/`, references in `docs/`.** A topic normally has one of each, cross-linked both ways. `notes/README.md` is the index for the guides — reading order, per-guide prerequisites, and the shared skeleton every guide follows; keep it current when adding or renaming a guide:
  - **`notes/` — from-first-principles teaching guides.** General concepts, largely portable beyond this repo: `communication-guide.md`, `network-stack-guide.md`, `can-guide.md`, `zephyr-build-system-guide.md`, `protobuf-guide.md`, `zbus-guide.md`, `sensor-api-guide.md`, `language-cpp.md`, `shell-guide.md`, `testing-guide.md`.
  - **`docs/` — terse project references.** Decisions, rationale, verified facts, and what was actually built here: `mqtt-design.md`, `network-bringup.md`, `can-bringup.md`, `build-system-overview.md`, `sensor-bringup.md`, `test-strategy.md`, `toolchain.md`.
  - Pairings: `communication-guide` ↔ `mqtt-design`, `network-stack-guide` ↔ `network-bringup`, `can-guide` ↔ `can-bringup`, `zephyr-build-system-guide` ↔ `build-system-overview`, `sensor-api-guide` ↔ `sensor-bringup`, `testing-guide` ↔ `test-strategy`. `protobuf-guide.md`'s reference half is `proto/node.proto` itself, which carries the decisions inline; `zbus-guide.md`'s is the header comment in `shared/app_channels.h`, same arrangement. `language-cpp.md` and `shell-guide.md` have no reference half.
  - **Exception:** `docs/firmware-mqtt-walkthrough.md` teaches, but it is a guided reading of *this repo's* `gateway/src/main.cpp` rather than a general concept, so it stays in `docs/` with the references — keep it in sync when the client changes.
  - Follow that split when adding a topic, and remember relative links cross the directory boundary (`../docs/…` from a guide, `../notes/…` from a reference). The user is learning these concepts, so **explain rather than assume** — don't take familiarity with a CLI, tool, or protocol for granted.
- Sensor access goes through Zephyr's sensor API, not raw I²C command codes. What the driver does underneath (command codes, conversion formulas, CRC-8 params) is documented inline where it matters in `notes/sensor-api-guide.md` and `docs/sensor-bringup.md` — reach for those when debugging the sensor path.
